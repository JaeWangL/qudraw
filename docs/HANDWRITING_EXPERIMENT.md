# 필기감 실험 기록

## 사용자가 말한 현상

2026-10-08, iPad + Apple Pencil에서 다음 두 현상을 모두 경험했습니다.

1. 펜을 뗐다가 다시 쓰는데 앞뒤 획이 붙어 보인다.
2. 손이 움직인 뒤 획이 따라오고 모양이 매끈하게 보정된다.

목표는 펜을 움직인 위치에 곧바로 잉크가 보이고, 펜을 뗄 때 획이 확실히 끝나는 것입니다. 끝부분의 약한 필압 변화·둥근 모양은 허용하되 원하는 정도는 사용자 비교로 정합니다. 브라우저 종류·iPad 모델·Pencil 세대·화면 주사율은 아직 확인되지 않았습니다.

## 현재 확인한 사실

비교 기준은 서비스에 설치된 Excalidraw 0.18.1 / perfect-freehand 1.2.0입니다. 최신 upstream master로 먼저 바꾸면 버전 차이와 개선 효과가 섞이므로 같은 버전에서 시작했습니다.

### 공간 보정

원본은 `streamline=0.5`, `smoothing=0.5`, `thinning=0.6`을 사용합니다. strokeWidth 0.5일 때 기본 size는 2.125 scene px입니다. roughness를 0으로 설정해도 이 보정은 별도로 남습니다.

perfect-freehand의 중심선 계산에 21개 점 `(0,0)…(100,0)`을 5px 간격으로 넣고 `last=false`로 계산한 결과:

| streamline | 마지막 중심선 x | 원래 입력점과 거리 |
| ---------- | --------------: | -----------------: |
| 0.5        |        96.30435 |          3.69565px |
| 0.1        |        99.53552 |          0.46448px |
| 0          |             100 |                0px |

이는 특정 합성 직선에서의 **알고리즘 공간 지연**입니다. 실제 기기의 시간 지연이나 모든 필기에서의 차이를 뜻하지 않습니다. 원본은 획 종료 시 `last=true`로 끝점에 도달합니다.

### 입력과 획 경계

- 원본 pointermove는 requestAnimationFrame 예약을 거칩니다. 같은 프레임에 들어온 추가 이벤트의 좌표를 모두 보존하지 않으며, coalesced events도 사용하지 않습니다.
- 정상적인 pointerup에서는 대기 중인 이동 핸들러를 flush합니다. 단순히 ‘penup 전에 rAF가 남아서’가 원인이라고 단정할 수 없습니다.
- pointerup을 받지 못한 뒤 다음 pointerdown으로 정리하는 경로에서는 **새 획 시작 좌표가 이전 획의 마지막 좌표로 들어갈 수 있습니다**. 원본에 pointercancel 종료 처리가 없어 이 경계를 보강해야 합니다. 실제 iPad 증상이 이 경로인지는 기기 기록으로 확인합니다.
- Pencil 시작 압력이 정확히 0.5일 때 원본은 실제 압력 대신 속도 기반 압력 시뮬레이션을 선택할 수 있습니다.

### 진단평가 앱의 별도 부하

저장 큐와 이미지 worker는 이미 있습니다. 다만 큐에 넣기 전의 동기 snapshot 복제·변경점 검사, 매 이벤트의 scene 순회, 경계 측정 등의 비용은 따로 측정해야 합니다. `180ms` 저장 주기는 화면 표시를 의도적으로 지연시키는 타이머가 아닙니다. 이번 독립 실험은 이러한 호스트 부하를 제외한 엔진 차이를 먼저 확인합니다.

## 사용자와 합의할 측정 기준

| 느낌 | 확인할 자료 | 해석의 한계 |
| --- | --- | --- |
| 획이 늦게 따라온다 | 입력 이벤트 나이, 처리 시간, 프레임 간격의 중앙값/p95 | 화면의 물리적 표시 지연은 고속 촬영이 필요 |
| 펜을 떼도 이어진다 | pointerdown/up/cancel 순서, 획 ID, 각 획 시작·끝 좌표 | 브라우저가 이벤트를 누락했는지 실제 기기에서 확인 |
| 글자가 지나치게 매끈하다 | 같은 글자의 기존/노트 모드 비교, 각진 모서리·끝점 | 정답 수치가 아니라 사용자의 선호 |
| 끝이 너무 두껍다 | 압력 기록, 획 끝 반경과 중간 두께, 사용자 비교 | Pencil 기종·압력 습관 영향 |

‘지연 0’이라고 보고하지 않습니다. 첫 실험에서는 보정에 의한 뒤처짐 제거, penup 이후 새 획 분리, 처리 p95의 상대 개선 여부를 확인합니다. 시각적 즉시성의 최종 판단은 사용자가 합니다.

## 2분 비교 순서

1. 같은 iPad·Pencil·브라우저·확대율에서 기존 모드와 노트 모드를 번갈아 사용합니다.
2. `가나다`, `ㅁㅁㅁ`, `1 + 1 = 2`, 작은 점 10개를 씁니다. 획 사이 펜을 짧게라도 확실히 뗍니다.
3. 빠른 지그재그로 모서리 보정과 뒤따라오는 정도를 봅니다. 마지막에는 원을 천천히 그려 미세 떨림이 불편한지 확인합니다.
4. 손바닥을 댄 상태, 캔버스 경계, 잠깐 다른 앱에 갔다가 돌아오는 경우에도 획이 연결되는지 확인합니다.
5. 세 항목을 따로 평가합니다: 뒤따라옴, 획 분리, 보정 강도. 한 점수로 합치지 않습니다.
6. 필요할 때 측정 JSON을 내보내고, 더 편한 모드와 불편한 글자/동작을 알려 주세요. 다음 반복에서는 한 가지 설정만 바꿉니다.

측정은 화면을 사용하는 현재 기기의 데이터입니다. 개발 머신의 마우스/합성 이벤트 테스트로 iPad의 필기감을 검증했다고 표시하지 않습니다. `getCoalescedEvents`는 브라우저와 secure context 지원 여부에 따라 제공되지 않을 수 있으며, 없는 경우 기본 pointer event로 동작해야 합니다.

## 나중에 서비스에 통합하기 전

필기 렌더링 프로필과 버전을 획별로 저장해야 합니다. 화면만 바꾸면 서버 이미지·OCR 캡처·선생님 복기·영상 내보내기가 서로 다른 외형이 됩니다. 진단평가 앱의 worker, replay schema, fingerprint, PNG/video 경로까지 같은 프로필을 사용하고 기존 기록의 모양은 보존하는 별도 작업이 필요합니다.

## 첫 구현과 검증 결과

2026-10-08의 `notebook` 프로필 v1은 streamline/smoothing 0, thinning 0.15, 실제 pen pressure를 사용합니다. 모드 선택은 새 획에만 영향을 주고, 각 획의 `customData.qudrawInk`에 버전·프로필·완료 여부를 저장합니다. 기존 획은 원래 렌더링을 유지합니다. 노트 모드는 가까운 양끝을 자동으로 닫는 원본 finalizer 동작도 사용하지 않습니다.

- 필기 엔진·저장 복원·획 경계 테스트 17개, 실험실 기록기 테스트 4개 통과.
- 저장소 전체 TypeScript, 실험실 TypeScript, 수정 소스 ESLint 통과.
- 실험실 프로덕션 빌드 통과. 원본의 큰 번들·모듈 지시문 경고는 남아 있으며 번들 경량화 완료를 뜻하지 않습니다.
- 개발 머신 Chrome에서 별도 두 획, 되돌리기·다시 실행, 모드 전환, JSON 다운로드를 확인했습니다. JSON에 별도 획 ID, 점과 필압, 완료된 notebook 프로필이 들어 있음을 확인했습니다.
- 위 브라우저 검사는 마우스 기반 기능 확인입니다. 이 자동 검증 시점에는 사용자 기기 실측과 주관적 평가가 없었습니다. 이후 받은 비교 피드백은 아래에 별도로 기록합니다.

현재 구현도 진행 중인 획의 배열 갱신과 React 렌더링을 사용합니다. 긴 획이나 많은 획이 쌓인 경우의 비용을 측정한 뒤 필요하면 별도의 실시간 잉크 레이어를 검토합니다. 첫 비교에서 물리적인 지연이 사라졌다고 결론 내리지 않습니다.

공간 지연 수치는 `node scripts/benchmark-ink.cjs`로 재현할 수 있습니다.
